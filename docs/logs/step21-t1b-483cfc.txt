== T1b: por que "paso" el canary sobre wcp-483cfc44d381 y wcp-dedb89ec3d3d (step-20) ==

RESUELTO — PROVEN (artefacto de clasificacion del harness, no gap de
inspeccion). El script canary de step-20 (t4a_engine.py) clasificaba
`blocked = (status == 403)`. Los dos "passes" eran OTROS rechazos fail-closed:

- wcp-dedb89ec3d3d (application/json+protobuf, body JSON valido
  [null,[5,1,...]]): el canary anadido al final hace el JSON invalido ->
  el processor JSON lo rechaza con **400** (misma clase que E11, rechazo
  de JSON malformado). Verificado hoy: aislado 400, batch 400, y en el
  artefacto commiteado de step-20
  (docs/logs/runs/s20-t4a-canary-engine/canary.json) su status es 400.
- wcp-483cfc44d381 (text/plain 100.254 B, clase patologica): el canary run
  de step-20 usaba KORTEX_ENGINE_TIME_BUDGET_MS=2000; este body solo ya
  cuesta ~6 s (y 17-24 s con canary) -> **503 kortex-decision=timeout**.
  El artefacto de step-20 registra status 503. Hoy, con budget 120 s,
  el mismo body+canary bloquea 403 en todas las variantes.

Experimentos de hoy (engine coraza v3.8.1, HEAD bd29b44, PL1, budget 120 s):
1. Aislado, 10 variantes (docs/logs/runs/s21-t1b-483cfc/engine-pl1.json):
   wcp-end 403 (22.8 s) | wcp-start 403 | wcp-mid 403 | wcp-trunc50K 403 |
   wcp-trunc10K 403 | wcp-amp-end 403 | wcp-eq-end 403 | wcp-jsonct-end 400
   (JSON invalido -> rechazo) | wcp-plain-only 200 (6.0 s) | control prosa
   100K+canary 403.
2. Replay exacto step-20 (headers manifest + path + query): 403.
3. Batch completo 100 ids: 99/100 con 403; dedb con 400 (rechazo, no pass).

CONCLUSION:
- NO existe ningun pass-through: ambos ids fueron RECHAZADOS (400/503) en
  step-20; la lectura "2 passes" fue un defecto de conteo del script canary
  (solo 403 contaba como bloqueo). Los 503/400 son fail-closed.
- El body de wcp-483cfc44d381 no suprime deteccion (PROVEN por 1-3).
- Correccion en cascada: el "JSON+protobuf REQUEST_BODY gap" de step-20
  (reports/step-20.md, docs/engine-design.md, docs/baseline-v1.5.md) queda
  RETIRADO como gap de evasion: un body JSON valido con payload en valor o
  clave se detecta via ARGS_JSON (matriz T1c: 403), y payload tras JSON
  valido -> 400. El hecho medido de step-19 T2 (el processor JSON no puebla
  REQUEST_BODY) sigue siendo cierto como hecho de variables, pero NO
  implica un gap de deteccion.
- Regla 49 (fix v3.8.1 "fixed empirically"): este hallazgo NO reabre el
  defecto flip: no hubo ningun 200 indebido. E30/flip_repro siguen en 0.
