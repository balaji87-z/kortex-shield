# Step-13 T7 evidence — Coraza latency pathology on wcp-80a49c991b2d

All runs in this file are DIAGNOSTIC (AGENTS.md rule 34). They never produce a
baseline or parity number. Hypothesis was written before the T6 experiment
(docs/decisions/0003-step13-t6-hypothesis.md); the T7 investigation below was
run after the T5/T6 results were known.

Sample: wcp-80a49c991b2d — POST, content type text/plain (no body processor),
body 477,231 bytes (481,798 with the runner's encoding). Only lengths are
printed here, never recorded values (rule 25).

## 5. Controls (DIAGNOSTIC)

Tool: tools/run_step13_t7_controls.sh; raw: docs/logs/step13-t7-controls.txt,
docs/logs/step13-t7-controls-b.txt.

- urlencoded control, same 477,231-byte size, allowed content type:
  1,848 / 1,995 / 1,691 ms, status 200 — fast (linear-ish), so body size alone
  does not cause the pathology.
- SecRequestBodyAccess Off (scratch container; mount + file verified inside the
  running container: "/opt/coraza/overrides/zz-t7.conf: SecRequestBodyAccess
  Off"): 5 / 4 / 3 ms, 403. The same request becomes 4 orders of magnitude
  faster. Note: the first attempt at this control (step13-t7-controls.txt)
  silently did not apply the override and still showed ~40 s; it was redone
  with in-container verification (step13-t7-controls-b.txt) and only the
  verified redo is used as evidence.
- SecRuleEngine DetectionOnly (rules still evaluated): 41,701 / 41,373 /
  44,287 ms, status 200 — blocking is not the cost.
- Direct POST to the stub backend (bypassing both engines): 3 / 2 ms — the
  backend is not the cost.
- ModSecurity at PL2 (PARANOIA=2, BLOCKING_PARANOIA=2, DETECTION_PARANOIA=2):
  68 / 29 / 27 ms, 403 (docs/logs/step13-t7-modsec-pl2.txt) — fast at PL1 and
  PL2.

## 6. Conclusions

- PROVEN (experiment: rule-disable bisect + RequestBodyAccess-Off control):
  the dominant cost of the 40+ s requests is Coraza engine-internal request
  body processing while SecRequestBodyAccess is On. No CRS rule is the
  dominant cost — removing all 8 matched body-derived rules left the latency
  unchanged (~40 s), and turning body access off dropped it to 3–5 ms.
- PROVEN (experiment: truncation series): the cost grows super-linearly with
  body size on this sample, approximately quadratic from 128 KB upward.
- PROVEN (experiment: 20-largest replay + content-type table): the pathology
  is content-dependent, not purely size-dependent — multipart bodies up to
  2.8 MB are fast (14–50 ms), while text/plain/empty-CT bodies from 156 KB
  upward and one urlencoded body at 958 KB take 2–44 s.
- PROVEN (experiment: PL2 replay): ModSecurity is fast on this sample at PL1
  and PL2 (7–92 ms), so the divergence is one-sided.
- HYPOTHESIS (unverified): the exact internal mechanism (which Coraza code
  path, e.g. buffer handling in the no-processor / urlencoded scan path).
  Not derived from source or a CPU profile; only the external behaviour is
  proven. Upstream coraza issues #1176 (performance drop with larger request
  bodies) and #1796 (body cost grows with rules x fields) document related
  cost growth; whether they are the same code path in coraza/v3 v3.7.0 is
  UNVERIFIED.
- Consistency with T6: T6 PROVED Coraza populates body-derived variables even
  for content types the policy rejects (text/plain etc.), while ModSecurity
  does not. The slow samples here are exactly the bodies Coraza scans and
  ModSecurity skips, which is consistent with both findings having the same
  underlying engine difference.
- Per rule 4, neither engine is called correct. Per rule 34, none of these
  numbers enter baseline or parity tables.
